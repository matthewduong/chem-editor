**ChemEditor audit — 11 September 2026**

Reviewed commit `2d02c08a0be714f2e8f8490e24484cebc931e2fc` (11 August 2026). The working tree was clean when the audit began. This report is the only intended tracked change; no application fixes were made.

**Assessment**

This is a substantial editor prototype with useful foundations for ChemDraw compatibility. It is not yet a drop-in replacement: several ordinary import, export, and clipboard paths can discard chemistry or document structure. The next milestone should establish trustworthy preservation and editing of existing drawings. Further expansion of QM, spectroscopy, and 3D features should follow that milestone or live in optional packages.

Keep the current stack. The preservation metadata, typed document objects, command layer, scene modules, generated font metrics, public fixtures, and real-ChemDraw harness are worth building on. A wholesale rewrite would discard useful work. The principal architectural change is to make the document the single authority and derive the canvas/chemistry views from it.

**Verified findings, in priority order**

1. **Critical: malformed imports can become a blank, successfully opened document.** `cdxmlToChemDrawDocument` uses `DOMParser` without checking for a parser error, the expected root, or valid pages. Both `<CDXML><page>` and `<not-a-chemdraw-file/>` produced an empty document with no warnings in the audit. `loadNative` catches load failures without returning a success/failure result, while the caller subsequently marks the selected path as saved. A later Save could therefore overwrite the source with an empty document. Reject invalid input before changing any editor or file state, and make load transactional. Evidence: [parser](/home/mrd/Code/chem-editor/src/utils/cdxml.ts:1753), [loadNative](/home/mrd/Code/chem-editor/src/components/ChemCanvas.tsx:3799), [open orchestration](/home/mrd/Code/chem-editor/src/App.tsx:1622).

2. **Critical: CDXML preservation does not preserve the whole document or all references.** The importer selects the first `<page>` and the exporter serializes `document.pages[0]`. A two-page drawing containing C on page one and O on page two imported as one page containing C, with no warning. A populated `<group>` lost its container on round-trip. Atom and bond IDs are regenerated while some raw reference attributes are emitted unchanged: a polymer fixture exported atom `102` as `1` but retained `BracketedObjectIDs="102"`. A separate example produced a fragment and atom both named `1`. Font-table IDs were excluded from that collision finding because they have their own context. Implement a document-wide object-ID registry, preserve original IDs where possible, rewrite understood references consistently, and preserve containers/pages structurally. Unknown references require conservative handling rather than blind renumbering. Evidence: [first-page serialization](/home/mrd/Code/chem-editor/src/utils/cdxml.ts:935), [ID assignment](/home/mrd/Code/chem-editor/src/utils/cdxml.ts:1136), [bracket metadata](/home/mrd/Code/chem-editor/src/utils/cdxml.ts:2905), [group handling](/home/mrd/Code/chem-editor/src/utils/cdxml.ts:3306).

3. **High: chemical interchange loses information.** `graphToMolblock` writes charges but omits isotope and radical records. A carbon atom with isotope 13 and one radical electron reimported as ordinary carbon. This writer also feeds chemical export and several RDKit operations, so the problem extends beyond a file-format label. The fixed-width geometry parser returned zero atoms for a valid one-atom V3000 input. The clipboard detector recognizes only V2000 molfiles. Introduce an explicit chemistry projection contract covering isotope, formal charge, radicals, aromaticity, atom mapping, query features, tetrahedral/double-bond/enhanced stereochemistry, and alias expansion. Unsupported chemistry should cause an explicit limitation or export refusal, not a plausible but different molecule. Test graph and stereochemical identity with an independent chemistry reader. Evidence: [molfile writer](/home/mrd/Code/chem-editor/src/lib/graph.ts:227), [geometry parser](/home/mrd/Code/chem-editor/src/lib/graph.ts:117), [clipboard detection](/home/mrd/Code/chem-editor/src/lib/clipboard.ts:93), [export caller](/home/mrd/Code/chem-editor/src/components/ChemCanvas.tsx:3877).

4. **High: the compatibility harness can pass after data has already been lost.** Its baseline is calculated after importing, exporting, and reimporting the source through ChemEditor. Loss during that first conversion is therefore outside the comparison. The summary counts element and bond categories but does not encode connectivity, formal charge, isotope, or radical state; changing all three atom properties left it identical in the audit. Some objects are deliberately excluded by capability. Visual comparison is opt-in, and the harness renders through the old SVG exporter. Retain this harness but compare the original source as well, use graph/stereo-aware assertions, validate references and containers independently, and compare source ChemDraw renderings against the actual application export. Test edited round-trips, not just open/save. Evidence: [baseline construction](/home/mrd/Code/chem-editor/scripts/run-chemdraw-tests.mjs:648), [summary](/home/mrd/Code/chem-editor/scripts/lib/chemdraw-harness.mjs:78), [visual mode](/home/mrd/Code/chem-editor/development/chemdraw-fidelity.md:23).

5. **High: clipboard operations are not document operations.** Copy and paste use a buffer containing only atoms, bonds, arrows, and text boxes. The CDXML paste route calls `cdxmlToState`, discarding native graphics, tables, embedded objects, and preservation metadata. Copying a selection consisting only of native objects also bypasses the flat selection checks. Copy first writes CDXML text and later writes a raster image in a separate asynchronous operation. The installed arboard macOS implementation clears the pasteboard when writing an image, so this is not a reliable way to publish simultaneous image and chemical representations. OS clipboard behavior was source-reviewed, not tested interactively. Implement document-subtree copy/paste with complete reference remapping and one platform-specific multi-format clipboard transaction. Evidence: [buffer](/home/mrd/Code/chem-editor/src/lib/clipboard.ts:5), [copy/paste](/home/mrd/Code/chem-editor/src/App.tsx:1824), [native image command](/home/mrd/Code/chem-editor/src-tauri/src/lib.rs:849).

6. **High: document safety needs completion.** The close button calls `appWindow.close()` directly; no application close-request or browser-unload dirty-document guard was found. The repository has no document autosave/recovery mechanism, and saves write directly to the selected path. Save completion marks the current revision saved after awaiting conversion/dialog/write, rather than marking the precise serialized snapshot; concurrent edits need a regression test. Add Save/Discard/Cancel handling for every document replacement and shutdown route, atomic writes with recovery, and revision-aware save completion. Evidence: [close button](/home/mrd/Code/chem-editor/src/App.tsx:4018), [file writes](/home/mrd/Code/chem-editor/src/lib/fileDialogs.ts:111), [save completion](/home/mrd/Code/chem-editor/src/App.tsx:1675), [saved revision](/home/mrd/Code/chem-editor/src/store/index.ts:1006).

7. **High: normal desktop builds delete user preferences.** `scripts/tauri-build.mjs` calls `clearPersistedSettings()` unconditionally, which removes the user's application `settings.json` before building. Build output should not depend on, or mutate, the developer's live application settings. Remove this behavior and use a temporary application-data directory for any reproducibility checks. The full build was deliberately not executed during this audit. Evidence: [deletion](/home/mrd/Code/chem-editor/scripts/tauri-build.mjs:28), [unconditional call](/home/mrd/Code/chem-editor/scripts/tauri-build.mjs:55).

8. **High: a fresh Python test environment fails.** The existing environment passed all nine Python tests. An isolated environment installed from the lockfile failed `test_optimize_hartree_fock_geometry_returns_atoms_and_bonds_for_h2` with `pyscf not installed`. PySCF is in the optional `nmr-dft` group, while the default test runner and CI do not request that group. Split base and QM integration suites, test the unavailable-feature behavior in the base suite, and run the integration suite in a CI job that installs the required group. Evidence: [dependency groups](/home/mrd/Code/chem-editor/src-tauri/pyproject.toml:18), [test](/home/mrd/Code/chem-editor/src-tauri/tests/test_orbitals.py:93), [runner](/home/mrd/Code/chem-editor/scripts/run-python-tests.mjs:18), [CI](/home/mrd/Code/chem-editor/.github/workflows/ci.yml:66).

**Architecture and maintainability**

The document and flat canvas arrays remain independently mutable, with two aligned undo histories. This complicates preservation, selection, grouping, clipboard behavior, and undo. Move editing operations behind document commands incrementally; make canvas arrays derived views, keep one history, and handle document style/page changes through the same transaction system. The command/index layers already provide a starting point. Evidence: [history updates](/home/mrd/Code/chem-editor/src/store/index.ts:655), [commands](/home/mrd/Code/chem-editor/src/editor/commands/index.ts:157).

Finish the renderer integration already started. `SvgCanvasContext` exists and is exercised by scene fixtures, but application print, SVG export, and clipboard still call the independent `generateCanvasSVG`. The latest commit explicitly acknowledges that it is not yet wired into the app. Port bounds, cropping, transparency, label knockouts, image/font readiness, and page handling deliberately, then remove the old committed-content renderer. Retain only the overlays needed for interaction. Evidence: [new backend](/home/mrd/Code/chem-editor/src/lib/svgCanvasContext.ts:124), [application export](/home/mrd/Code/chem-editor/src/components/ChemCanvas.tsx:3844), [print rendering](/home/mrd/Code/chem-editor/src/App.tsx:944).

The current worker import path cannot do its intended work in a normal browser worker: it calls the parser that requires `DOMParser`, with no worker-compatible implementation supplied. Executing the built worker in a context without DOM globals returned `DOMParser is not defined`; the async wrapper silently falls back to parsing on the main thread. The HTML standard exposes `DOMParser` to Window. Adopt a parser that works in workers, and test worker execution explicitly. Add operation cancellation and stale-result handling before relying on this path for large documents. Evidence: [worker](/home/mrd/Code/chem-editor/src/workers/cdxmlWorker.ts:15), [fallback](/home/mrd/Code/chem-editor/src/lib/chemdrawDocumentCommandsAsync.ts:15), [HTML interface definition](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html#domparser).

`ChemCanvas.tsx` is 7,202 lines and `App.tsx` is 5,615 lines. Extract document lifecycle, clipboard, export, menus, and editing workflows into bounded modules as they are fixed. The purpose is to make behavior independently testable and remove duplicate authority; a cosmetic file split alone will not achieve that.

**What full interoperability needs to mean**

Publish a compatibility matrix keyed by ChemDraw version, operating system, file/clipboard format, and feature. Distinguish editable support, preserved opaque content, visual-only support, and rejection. The existing capability mechanism is a useful foundation, but the current reference-loss reproductions show that preservation needs stronger guarantees.

| Surface            | Current evidence                                                        | Required milestone                                                              |
| ------------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| CDXML documents    | Substantial typed import/export, with page/container/reference losses   | Preserve complete documents and validate all supported edits                    |
| Binary CDX         | No CDX file path or binary codec found                                  | Document-preserving CDX reader/writer and corpus tests                          |
| ChemDraw clipboard | CDXML text plus separate image write; flat internal buffer              | Native formats in both directions, multiple representations in one transaction  |
| Word/PowerPoint    | No editable embedded-object integration found                           | Test editable transfer and reopen workflows, separately from image paste        |
| MOL/SDF            | V2000 projection; isotope/radical losses; SDF reader takes first record | V2000/V3000 chemistry fidelity, explicit multi-record/data-field policy         |
| RXN/reactions      | Export heuristically classifies fragments from the first arrow          | Explicit reaction steps, participants, agents, atom maps, and RXN import/export |
| SVG/PNG/print      | Scene renderer and old SVG path differ                                  | One export draw path, stable fonts, physical sizing, multipage print/export     |

Do not assume RDKit can supply full document interoperability. Its current documentation explicitly limits CDXML handling to the functionality needed for molecules and reactions; CDX support and writing also depend on an optional ChemDraw parser build. Use RDKit for chemistry validation/conversion while retaining a document-preserving codec. See [RDKit CDXML parser documentation](https://www.rdkit.org/docs/cppapi/namespaceRDKit_1_1v2_1_1CDXMLParser.html).

Native clipboard work is a distinct product requirement. Revvity's own documentation distinguishes native clipboard transfer from manually transferring CDXML text. A workflow requiring users to choose “Copy as CDXML” can be useful initially, but should be described as an explicit workaround in the compatibility matrix. See [ChemDraw JS clipboard FAQ](https://revvitysignals.com/sites/default/files/2024-12/rs-faq-ChemDraw_JavaScript.pdf).

Treat Office integration as its own platform project, especially existing editable objects and double-click editing. Test Windows and macOS behavior independently. Linux can still provide useful file interchange and high-quality vector output while platform-specific embedded-object milestones remain outstanding. Do not equate successful image paste with editable chemistry transfer.

Reaction chemistry also needs a proper model. The CDXML importer infers roles from the first reaction arrow. RXN export uses horizontal centroids and the first arrow direction, not explicit reaction-step membership; vertical and multistep schemes need special attention. SDF import takes only the first record and returns no data fields; export returns a mol block without an SD record delimiter or properties. Define and test these format contracts rather than silently treating every format as one drawing molecule. Evidence: [reaction inference](/home/mrd/Code/chem-editor/src/utils/cdxml.ts:3336), [SDF input](/home/mrd/Code/chem-editor/src-tauri/bin/chem-engine.py:335), [RXN/SDF export](/home/mrd/Code/chem-editor/src-tauri/bin/chem-engine.py:358).

**Open-source and distribution readiness**

No project-level license file or license field was found, although dependency notices and a font license exist. Choose a project license before inviting reuse/contributions; dependency notices do not license the application's own code. Add a root README with screenshots, installation instructions, compatibility limits, and contribution guidance. GitHub explains the distinction between publishing source and granting reuse rights in its [repository licensing guidance](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository).

Separate the drawing application from optional scientific compute/data components. The staged HOSE SQLite database alone is approximately 793 MiB on this machine. Normal desktop preparation downloads source data and installs/builds QM dependencies; this is a large barrier to drawing-only contributions and releases. Ship a lightweight core, version optional data/compute packages, and document their provenance and redistribution terms. CI should produce and smoke-test installable desktop artifacts on supported operating systems. Current CI tests JS on three operating systems but compiles/tests Rust only on Linux and does not exercise a full packaged sidecar release.

Update stale operational documentation. `development/README.md` says the public repository ships no CDXML fixtures, but it now contains 18 public fixtures. `CLAUDE.md` describes groups as existing only in flat arrays, but there is also a document-group implementation; serialization is still incomplete. Verify support statements against release artifacts rather than old notes.

**Recommended implementation order and acceptance gates**

| Order | Work                                                                                                                | Done when                                                                                                                                                                                        |
| ----- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1     | Document safety: invalid input, transactional open/save, close protection, build side effects, fresh-environment CI | Bad files leave the current document and path untouched; edits during save remain dirty; closing cannot silently lose work; builds preserve settings; clean CI passes                            |
| 2     | Preservation: stable IDs/references, all pages, groups, source-aware compatibility checks                           | No-op and edit/save round-trips preserve the original document's supported chemistry, containers, references, and opaque payloads; known unsupported content is explicitly handled               |
| 3     | One document authority and one export renderer                                                                      | Copy/paste/undo work across all supported object types; live drawing, SVG, PNG, and print agree on a gated public visual corpus                                                                  |
| 4     | Chemistry and interchange: isotope/radical/stereo fidelity, V3000, CDX codec, native clipboard                      | Independent readers confirm chemistry; two-way ChemDraw tests pass for each claimed format and platform                                                                                          |
| 5     | Pilot release and Office work                                                                                       | Installers work on clean machines; a chemist can open an existing scheme, edit it, exchange it with a ChemDraw collaborator, and use it in a manuscript/presentation with documented editability |

License/README work and separating optional compute packaging can proceed alongside these milestones. Implementing the first preservation regressions and repairing the test oracle is a better immediate task than adding another analysis panel. Use a public synthetic corpus for every pull request, and private real-ChemDraw cases for release acceptance. Organize cases by semantic feature, not an arbitrary first-N alphabetical sample.

For chemistry acceptance, include isotopic labels, radicals, salts, aromatic/query/dative bonds, aliases, R groups, tetrahedral and double-bond stereo, enhanced stereo groups, polymers, mapped multistep reactions, and disconnected structures. For document acceptance, include multiple pages, nested groups, rich text, fonts, images, tables, unknown objects, copy/paste with fresh IDs, delete/undo, and edits to documents containing opaque metadata. Add a test that intentionally corrupts each invariant to establish that the oracle actually detects it.
